## Part 2 — A Specific Bug

**2a. Describe the hardest bug you fixed this semester. Not the most recent one — the one that took 
the longest or cost you the most confusion. What was the symptom? What did you think the problem was
at first? What was it actually? How did you find it?**

The hardest bug for me was the Search screen returning way more results than it was supposed to. I 
was expecting around 60 results but at one point I was getting around 3,600. At first I thought 
something was wrong with the API and that the server was actually sending me too many results.

The real problem was how I was handling the results in the app. When I was loading pages, I was 
adding and flattening results in a way that caused the same results to be added multiple times. 
This was confusing because the API request itself could work correctly while the number displayed 
in the app was completely wrong.

What helped me figure it out was looking at where the results were being added instead of only 
looking at the API response. That taught me that when something looks like an API problem, the 
problem can actually be what your own code does with the response after receiving it.

**2b. Copy and paste the specific lines of code you changed to fix it. (This can be a before/after 
comparison, a diff, or just the relevant snippet.) Explain in plain English what the fix does and 
why it works.**

private var nextStart = 20
private var hasMore = true
private var isLoading = false

fun loadNextPageIfNeeded() {
if (!hasMore || isLoading) return

    isLoading = true

    val filteredResults = getFilteredResults()
    val nextPage = filteredResults.drop(nextStart).take(20)

    _results.value = _results.value + nextPage

    nextStart += 20
    hasMore = nextStart < filteredResults.size

    isLoading = false
}

private fun resetFakeSearch() {
nextStart = 20
hasMore = true

    val filteredResults = getFilteredResults()
    _results.value = filteredResults.take(20)

    hasMore = filteredResults.size > 20
}

The fix was making sure the search results loaded 20 at a time instead of continuing to add the same
results over and over. nextStart keeps track of where the next group of results should start, and 
after 20 more results are loaded it increases by 20. I also used isLoading so another page cannot 
start loading while one is already being loaded, and hasMore stops it when there are no more 
results. When the user changes their search or filter, resetFakeSearch() starts the results over 
from the first 20. This fixed the problem I was having with the number of search results getting 
way higher than it was supposed to.

## Part 3 — What You Actually Learned

**3a. Pick the concept from this semester that took the longest to actually understand — not just to
implement, but to understand. Describe what you thought it was before you understood it, what 
changed, and how you would explain it now to a student who was exactly where you were at the start 
of the semester.**

The concept that took me the longest to understand was how the screen, ViewModel, repository, and 
API all work together. At first I understood that the API was where the information came from and 
the screen was where it was displayed, but I did not really understand everything that happened 
between them.

It started making more sense when we stopped using hardcoded information and started connecting our
screens to the actual API. I learned that the repository is responsible for getting the information
the ViewModel keeps track of the information and the state of the screen, and then the screen 
displays it.

If I was explaining it to someone who was where I was at the beginning of the semester, I would tell
them not to think of everything as separate pieces. The screen, ViewModel, repository, and API are 
basically a flow. The screen needs something, the information gets retrieved, the ViewModel keeps 
track of what is happening, and then the screen updates based on the result.

@Test
fun `like and unlike public quote updates state`() =
runTest(dispatcher) {

        val viewModel =
            QuotesViewModel(
                application = application,
                repository = repository
            )

        dispatcher.scheduler
            .advanceUntilIdle()

        viewModel.loadQuotes(
            QuotesMode.PUBLIC
        )

        dispatcher.scheduler
            .advanceUntilIdle()

        viewModel.toggleLike(1)

        val likedState =
            viewModel.uiState.value
                    as QuotesUiState.Success

        assertTrue(
            1 in likedState.likedQuoteIds
        )

        assertEquals(
            1,
            likedState.quotes
                .first()
                .likeCount
        )

        dispatcher.scheduler
            .advanceUntilIdle()

        coVerify(
            exactly = 1
        ) {
            repository.likeQuote(1)
        }

        viewModel.toggleLike(1)

        val unlikedState =
            viewModel.uiState.value
                    as QuotesUiState.Success

        assertFalse(
            1 in unlikedState.likedQuoteIds
        )

        assertEquals(
            0,
            unlikedState.quotes
                .first()
                .likeCount
        )

        dispatcher.scheduler
            .advanceUntilIdle()

        coVerify(
            exactly = 1
        ) {
            repository.unlikeQuote(1)
        }
    }
I picked this test because it makes sure liking and unliking a public quote actually works. When I 
like the quote, it checks that the like count goes up to 1 and that the quote is shown as liked. 
When I unlike it, it makes sure the like count goes back to 0 and the quote is not shown as liked 
anymore. It also makes sure the repository is called for both actions.

This test proves that the like and unlike feature is working correctly, but it does not prove that 
the whole Quotes feature works. It does not test things like editing, deleting, loading more quotes,
